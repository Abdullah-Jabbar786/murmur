# Test files and metadata (H1.2)

`peer/metadata.py` implements the test-file generator and metadata tool from
`MASTER_PLAN.md` section 7.2. Defaults match `config/default.json`: a 64 MiB
file, split into 256 pieces of 256 KiB each. These are local input files for
the future seed and leechers; this tool does not transfer them over a network.

## Generate a dataset

Run from the repository root in PowerShell:

```powershell
.\.venv\Scripts\python.exe -m peer.metadata --size 64MiB --seed 42
```

This creates `testdata/payload.bin` and `testdata/metadata.json`, then prints
the byte length, piece count, piece length, and hexadecimal `info_hash`.
`testdata/` is already ignored by Git. Do not commit the generated payload.

For a smaller development dataset with separate output paths:

```powershell
.\.venv\Scripts\python.exe -m peer.metadata --size 8MiB --seed 42 --output testdata/dev/payload.bin --metadata testdata/dev/metadata.json
```

`--size` accepts an integer number of bytes or an integer with `KiB`, `MiB`,
or `GiB` suffix (case-insensitive). `--piece-length` overrides bytes per piece;
use the default 262144 for normal project runs. Empty files are supported.

Both output paths must be different and unused. An existing output causes an
error without overwriting it. Newly created partial outputs are removed if
generation fails; newly created directories may remain. Files are not published
as an atomic pair: wait for successful command completion before using them.
To generate again, choose a new directory or deliberately remove your old data.

## Metadata and identity

The JSON has exactly four fields:

| Field | Meaning |
|---|---|
| `name` | Filename, without parent directories |
| `length` | Total file length in bytes |
| `piece_length` | Full piece length in bytes |
| `pieces` | Ordered list of lowercase, 64-character SHA-256 hex digests |

The final piece may be shorter; its hash covers only its actual bytes, with no
padding. An empty file has an empty hash list. The loader rejects malformed
JSON, duplicate/unknown fields, invalid filenames and numeric fields, incorrect
hash counts, and invalid hash strings.

Canonical JSON uses lexicographically sorted keys, compact comma/colon
separators, literal Unicode encoded as UTF-8, and no BOM or final newline.
`info_hash` is SHA-256 of those canonical bytes. It is derived, not stored in
the JSON itself. Loading pretty-printed JSON or reordering its keys preserves
identity. Renaming the payload in metadata, changing piece length, or changing
any piece hash changes identity. There is no Unicode normalization of filenames.

The generator uses a private `random.Random(seed)` with a nonnegative integer
seed (default 42). It calls `randbytes` in fixed 64 KiB chunks, followed by one
short final chunk. The same seed, size, filename, and piece length reproduce
the same dataset and identity under this algorithm. Hashing piece length does
not affect generated bytes. These are pseudorandom test bytes, not secrets.
Generation uses 64 KiB buffers; hashing reads at most 1 MiB at a time.

## Python integration

```python
from peer.metadata import build_metadata, load_metadata
from peer.wire import Handshake, encode_message

metadata = load_metadata("testdata/metadata.json")
# Verify the complete local payload by independently hashing it:
assert build_metadata("testdata/payload.bin",
                      piece_length=metadata.piece_length) == metadata

# info_hash is binary for the handshake; info_hash_hex is for display/logs.
packet = encode_message(Handshake(metadata.info_hash, b"p" * 20),
                        num_pieces=metadata.num_pieces)
```

`load_metadata` validates structure, not the contents of a separate payload.
Use trusted metadata; piece verification during downloads belongs to H1.4.
The generator has a second sequential pass to hash the file it just wrote.

## Tests

Use a fresh temporary path to avoid old Windows pytest directory permissions:

```powershell
$testTemp = Join-Path $env:TEMP ("murmur-tests-" + [guid]::NewGuid().ToString("N"))
.\.venv\Scripts\python.exe -m pytest tests/test_swarm_metadata.py -v -p no:cacheprovider --basetemp="$testTemp"
```

Expected: 54 passed. The acceptance test generates two 64 MiB files in pytest's
temporary directory, checks all 256 hashes independently, and compares their
bytes and metadata. Other tests cover a fixed seed vector, partial/empty files,
canonical identity, handshake compatibility, malformed input, output collisions,
failure cleanup, and the CLI. The acceptance test needs about 128 MiB of
temporary disk space; pytest may retain temporary files after a successful run.
